# Getting Started

This page gives a minimal, repeatable path to first use and a "2 months later" reminder workflow. It assumes you have a project containing source in one of the supported languages (Python, JavaScript, TypeScript, Rust).

See root `README.md` (Install + Quick Start + Development sections) and `spec.md` (CLI Contract) for the absolute basics. This page adds the "why these steps" and ties to config/concepts.

## Prerequisites

- Python 3.10+ (the host for the CLI).
- For full language support: the appropriate tree-sitter grammar wheels (installed automatically with the package on most connected machines; Python-only works without them — see `src/crap4code/languages/registry.py` for the lazy/tolerant loading design).
- A source tree (the directory containing your `pyproject.toml`, `Cargo.toml`, `package.json`, etc. is the natural "root").
- (Optional but recommended for real CRAP) A coverage report artifact generated by your normal test/CI process.

Cross-platform note: The same `python -m pip ...` and `crap4code` (or `python -m crap4code`) commands work on pwsh, cmd, bash, zsh, etc. See root `README.md` "Windows and Cross-Platform Notes" and the comments emitted by `crap4code init`.

## First-Time Setup (One-Time)

1. **Install for use or development** (from the project or a temp clone):

   ```powershell
   # Windows (pwsh or cmd) or POSIX
   python -m pip install -e .[dev]
   # or for a released version (once on PyPI): python -m pip install crap4code
   ```

   After this you have the `crap4code` entry point. The `python -m crap4code` form also works everywhere thanks to `src/crap4code/__main__.py`.

2. **cd to your project root** (the dir that will contain `.crap4code.toml` next to your `src/` or equivalent).

3. **Generate the sample repo-local config** (never overwrites without `--force`):

   ```powershell
   crap4code init
   # or explicitly
   crap4code init --force --config .crap4code.toml
   ```

   This writes `.crap4code.toml` containing the canonical sample (see `src/crap4code/core/config.py:sample_config_text`). The top of the file is a long comment block explaining the shell execution model, `python -m` preference, `&&` chaining, `--report-only` safety valve, and cross-platform realities. **Read those comments** — they are the primary durable documentation for coverage commands.

4. **Edit the generated `.crap4code.toml`** (critical step):

   - Set `paths` under each language section (or rely on `[scan] default_paths`).
   - Add `coverage_report` + `coverage_format` if you have (or will generate) a report.
   - Optionally set a `coverage_command` (see configuration.md and the sample comments).
   - Adjust `[scan] threshold` if the default (8.0) does not suit your project.

   Example minimal edit for a Rust workspace that uses `crates/` instead of `src/` and already produces lcov:

   ```toml
   [rust]
   paths = ["crates"]          # directories, not individual files
   coverage_report = "target/debug/lcov.info"
   coverage_format = "lcov"
   # coverage_command left unset because we generate coverage in normal CI/test runs
   ```

   See [configuration.md](./configuration.md) for full details on every key and why paths are directories + recursive.

5. **(Optional) Generate or locate a coverage report** so you get real CRAP numbers instead of `N/A`.

   - Python projects often use `coverage.py` XML.
   - JS/TS/Rust commonly use LCOV (e.g. from `cargo-llvm-cov`, `nyc`, etc.).
   - The report is just a "receipt" of which lines were executed by tests. See [concepts.md](./concepts.md).

6. **Run your first scan** (use `--report-only` while learning or on CI that should not mutate state):

   ```powershell
   crap4code scan --report-only
   crap4code scan --lang python --format json
   crap4code scan --changed --base-ref origin/main   # only files touched vs. base
   crap4code scan --changed --report-only --baseline baseline.json  # progress vs prior full scan on just the parts you edited
   ```

   Output is a risk-sorted table (or stable JSON). Warnings (if any) go to stderr after the main output. Exit code 2 means at least one *measured* CRAP exceeded the threshold.

## Typical "Away for 2 Months" Reminder Workflow

When you (or an agent) return to the project:

```powershell
cd /path/to/your/project-root   # the one with Cargo.toml / pyproject.toml etc.
crap4code init --force          # safe refresh of sample (or just inspect your existing .crap4code.toml)
# ...quickly review/edit paths + coverage_* keys if layout or tooling changed...
crap4code scan --report-only    # or without if you want the configured command to re-run
```

- The tool always looks for `.crap4code.toml` (or the path given by `--config`) in the current working directory (treated as root).
- If no config exists it synthesizes defaults for whatever languages the runtime registry can provide (`src/crap4code/core/config.py:load_project_config`).
- Use `crap4code scan . --lang rust` (explicit path + lang) as a one-off override without touching the TOML.

## Verifying It Works (Smoke)

- On a Python-only checkout or after simulating missing grammars: `crap4code scan --lang python --report-only` should succeed; `--lang rust` should print a clear message and exit 1 (no traceback).
- Full end-to-end with sample projects (used by release verification): the checked-in `tests/sample_projects/*` contain tiny source + coverage artifacts so `crap4code` behavior can be asserted without every toolchain present.
- Tests: `python -m pytest -q` (works from repo root on any shell after/before editable install thanks to the guard in `tests/conftest.py`).

## Common First Gotchas (Pointer)

- "No matching source files found." → normal when the discovery walk finds zero files with the expected extensions under the configured paths. Fix by editing `paths` in the TOML or passing explicit paths on the CLI. See [concepts.md](./concepts.md) and [troubleshooting.md](./troubleshooting.md).
- Coverage stays "indeterminate" / CRAP = N/A → expected until a matching report is configured and loadable. Complexity, risk (complexity-only fallback), and recommendations are still produced.
- On Windows: coverage commands always execute under `cmd.exe` (via `ComSpec`) even if you are in pwsh. The sample config and error diagnostics are written to make this visible. Prefer `python -m ...` forms.
