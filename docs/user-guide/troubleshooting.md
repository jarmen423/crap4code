## "No Matching Source Files Found."

**Symptom**: Scan prints this message and exits 0 (sometimes with warnings on stderr).

**Why it happens (normal, not a bug)**:

- Discovery (`src/crap4code/core/files.py`) builds a list of candidate roots from either CLI positional paths or the config's per-language `paths` (falling back to `[scan] default_paths`, which defaults to `["src"]`).
- It walks (files are taken as-is; dirs use `rglob`), resolves, and keeps only regular files whose suffix (`.lower()`) is in the language's extension tuple.
- After filtering (and optional git-changed intersection) the set is empty → early return with the message.
- Even on this path, any warnings collected during discovery (e.g. git problems when `--changed` was used) are printed to stderr (see the special handling in `cli.py:_scan` after the `if scanned_files == 0` check).

**Common triggers**:

- Running from repo root while the TOML still says `paths = ["src"]` (or default) but your code lives at the root or under `crates/`, `lib/`, `app/`, `packages/...`.
- `--changed` in a non-git directory or with a base ref that yields zero overlapping files (git warning will accompany the message).
- Selecting a language whose files are not under the paths you gave (e.g. `crap4code scan --lang rust` when all `.rs` are under `crates/` but config has `["src"]`).
- Explicitly passing a directory containing only non-matching files or no files.

**Fixes**:

- Edit the relevant language section in `.crap4code.toml` (preferred for repeatability):

  ```toml
  [rust]
  paths = ["crates", "examples"]   # list of directories; recursive search
  ```

- Or use CLI override for a one-off: `crap4code scan . --lang python` or `crap4code scan crates/ --lang rust`.
- For flat projects: `paths = ["."]`.
- For monorepos: list multiple entries.

See [concepts.md](./concepts.md) for the full "No matching..." explanation and [configuration.md](./configuration.md) "Paths — What They Actually Mean".

## Coverage Warnings and Indeterminate Results

**Symptom**: Many (or all) rows show `coverage = N/A`, `crap = N/A`, `coverage_state = indeterminate`; a warning like "Coverage report was not available or could not be mapped: path=... format=..." appears on stderr; or "Case-insensitive coverage path match used: ...".

**Why (design, not failure)**:

- A report is only loaded when **both** `coverage_report` and `coverage_format` are set for the language *and* the file exists at scan time.
- Mapping (`CoverageDatabase.coverage_for`) requires an exact (or case-fold-fallback) match on the normalized repo-relative path **and** at least one instrumented line from the report falling inside the parser-reported function range.
- If either side is missing or the intersection is empty → `("indeterminate", None)`. `calculate_crap` is never called. This is the "never invent" guarantee (see `docs/contracts.md`, `AGENTS.md`, `README.md`).
- Case-fold fallback (added for Windows R1) succeeds on many mismatches but records an auditable warning the first time a (folded, original) pair is seen. The warning is harmless and expected on case-insensitive filesystems.
- The report is a static artifact from a previous test run. If your test command or coverage generator changed output location / format / included files, the configured values will no longer match.

**Warnings vs. errors**:

- These situations produce warnings (collected and printed) rather than hard failures so that complexity-only analysis + recommendations remain available.
- Exit code is still 0 or 2 based only on measured CRAP; an unmappable report never forces exit 1.

**Fixes / checks** (in order):

1. Confirm the report file actually exists at the path written in the TOML (relative to the cwd you run crap4code from, or absolute).
2. Confirm `coverage_format` exactly matches one of the two supported strings: `"lcov"` or `"coverage.py-xml"` (case-insensitive match inside the loader).
3. Re-generate the report with your normal test/CI command, then run `crap4code scan --report-only` (avoids re-running the command while you debug).
4. Compare the exact normalized path strings:
   - Look at the `file` column in crap4code output.
   - Look at the `SF:` lines (LCOV) or `filename=` attributes (XML) inside the report.
   - They must match after `normalize_repo_path` (POSIX, repo-relative). Casing differences are now tolerated with a warning.
5. For workspace / monorepo layouts, make sure the `paths` in the language section cause discovery to walk the directories that the coverage tool actually instrumented (coverage tools often record paths relative to their own root or build dir).
6. If using `--report-only` during tuning, verify the artifact was produced by the right coverage tool invocation (e.g. the XML must have been emitted by `coverage xml`, not just the `.coverage` binary file).

See `src/crap4code/core/coverage.py` (the `coverage_for` case-fold logic, the two parsers, `load_coverage_database`) and `_apply_coverage` in `cli.py`.

## Workspace / Non-Standard Layout Issues ("paths" surprises)

**Symptom**: Correct language, report exists, but still mostly indeterminate or "no files".

**Root cause**: `paths` values are the directories the discovery walker starts from. If they do not contain (or are not ancestors of) the actual source files that the coverage report was generated against, you get zero overlap.

**Examples and fixes**:

- Rust workspace with crates: `paths = ["crates"]` (or list the specific crate dirs). Do not leave the default `["src"]`.
- Python package where tests live elsewhere and you want to measure the tests themselves: add `"tests"` (as the canonical Python sample does).
- Flat single-file or single-dir project: `paths = ["."]`.
- Coverage generated from a build/ or target/ dir that records absolute or differently-rooted paths: either make the report paths relative to the same root you pass to crap4code, or use absolute paths in the TOML (supported).
- Mixed monorepo: give each language its own `paths` list; run without `--lang` to process everything.

Discovery is deliberately simple (walk + suffix filter + optional git intersect). It does not try to parse `pyproject.toml` package includes, Cargo workspace members, etc. You tell it where the files are.

See [configuration.md](./configuration.md) and `src/crap4code/core/files.py`.

## Shell / Coverage Command Surprises (Especially Windows)

**Symptom**: `coverage_command` "works in my terminal" but fails or behaves differently when run by crap4code; or you get rich diagnostics mentioning `ComSpec`, `cmd.exe`, `pwsh -Command`, etc.

**Why**:

- The exact string from the TOML is executed with `subprocess.run(command, cwd=root, shell=True, env=os.environ.copy(), ...)`.
- On Windows (`os.name == "nt"`): `shell=True` **always** means `cmd.exe` (the value of `ComSpec`), no matter what interactive shell launched crap4code (pwsh, Git Bash, VS Code terminal, etc.).
- On POSIX: the platform default (usually `/bin/sh` semantics).
- Your aliases, functions, current shell's quoting rules, and interactive profile do **not** apply.
- The environment seen by the command is a copy of whatever environment launched the Python that is running crap4code (desktop shortcuts, scheduled tasks, CI steps, and some IDE launchers can have surprising PATH or no venv).

**Evidence in output** (when a command fails):

- Prefixed block: "Platform shell: ... (ComSpec=..., SHELL=...)", "Command: '...'", "cwd: ...", "returncode: ...", captured stdout/stderr.
- Extra actionable hint in the CLI layer about preferring `python -m` forms or explicit wrappers.

**Fixes / practices** (also documented in the generated config header):

- Prefer `python -m pytest ... && python -m coverage ...` (and similar) so the same Python/venv that is running crap4code is reused.
- For PowerShell-specific syntax: wrap the whole thing: `coverage_command = "pwsh -Command 'python -m ... ; python -m ...'"`.
- For cmd.exe needs: `cmd /c "..."`.
- Use `crap4code scan --report-only` while debugging a new command (completely skips execution).
- Activate your venv in the terminal before invoking crap4code.
- After a failure, read the exact diagnostics block — it tells you what was *actually* executed.

See `src/crap4code/core/coverage.py:run_coverage_command` (the diagnostics construction) and the "COVERAGE COMMAND SHELL MODEL" section of the sample produced by init. Root `README.md` has a dedicated "Coverage Commands on Windows (Shell Model)" subsection.

## Case Sensitivity on Windows (and Some macOS)

**Symptom**: Report clearly covers the function, paths look "the same", but you still get indeterminate (until the case-fold warning appears).

**Cause**: Source discovery records casing from the real FS walk (`Path.resolve()`). Coverage report parsers record casing exactly as written inside the report (`SF:` or `filename=`). `CoverageDatabase` does exact dict lookup first.

**Mitigation (current)**:

- Both sides are normalized to POSIX repo-relative keys.
- Case-fold fallback search is performed on miss (portable, not Windows-only).
- When fallback succeeds, a warning of the form "Case-insensitive coverage path match used: queried 'Src/Foo.py' against report key 'src/foo.py'." is emitted (once per unique pair).
- Displayed `file` values are the normalized ones from discovery, so you can diff them directly against the report.

**Limitation**: There is no automatic "always case-insensitive" mode that hides the difference; the warning keeps the behavior auditable. Compare the exact strings when you see indeterminate rows that "should" have been measured.

See `src/crap4code/core/coverage.py:coverage_for` (the folded loop) and the R1 section of the plan for background.

## Tree-Sitter / Language Availability

**Symptom**: `ModuleNotFoundError` or "Rust support requires `pip install tree-sitter-rust`..." on import or `--lang`.

**Reality**:

- Python analyzer is unconditional (stdlib `ast` only).
- JS/TS/Rust require their grammar wheels (real native `.pyd` on Windows). These are hard dependencies of the installed package today.
- The registry loads them lazily and tolerantly inside `get_language_registry` (try/except around the analyzer class import + construction). Missing ones simply do not appear in the returned dict.
- Explicit `--lang` for a missing one produces the helpful message and exit 1.
- Default scans (no `--lang`) simply omit unavailable languages.

**Workarounds**:

- For Python-only use: install works; `--lang python` is always safe.
- In restricted / air-gapped / corporate / arm64-Windows / future-Python environments: you may only get a subset. The tool remains usable for the languages that *are* present.
- To simulate: `pip uninstall -y tree-sitter-javascript tree-sitter-typescript tree-sitter-rust` then test the python path + graceful rust message (this is exercised in release verification per `docs/release-checklist.md`).

See `src/crap4code/languages/registry.py` (detailed module docstring) and the analyzer `__init__` files.

## Other Observed Behaviors

- **Stale `.coverage` locked on Windows**: cleanup now uses `shutil.rmtree(..., onerror=...)` + per-file `missing_ok=True` unlink and collects warnings instead of raising. The scan continues.
- **Wide table output**: expected on real codebases (67+ functions). Use `--format json` for agents or post-processing.
- **Git warnings with --changed**: now visible even on the "no files" path. The warning text contains the exact phrase to grep for in CI logs.
- **Config changes not taking effect**: make sure you are running from the directory that contains the `.crap4code.toml` you edited, or pass `--config` explicitly. The tool treats cwd as root.

## When to Use --report-only vs. Letting the Command Run

- Use `--report-only` for: exploration, config tuning, read-only CI, re-analysis after someone else produced the artifact.
- Let the command run when: you have a `coverage_command` configured and you explicitly want crap4code to be the thing that produces the fresh report as part of the scan (rare; most projects already have coverage in their normal test script).

The design intentionally makes the "just read what is there" path first-class and safe.

If a situation is not covered here, the combination of:

- the warnings printed by the tool,
- the rich diagnostics on coverage command failure,
- the comments in the generated `.crap4code.toml`,
- the docstrings and inline comments in `src/crap4code/core/*` and `languages/`,
- and the contracts in `spec.md` / `docs/contracts.md`

...should give you (or an agent) enough signal to diagnose without external help. The "never invent coverage data" and "deterministic/auditable" rules are the north star that explains many "why didn't it just figure it out?" moments.
